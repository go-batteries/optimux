# Changelog

- Using libvips since its benchmarks are better and no need for process spawn
- Remove caching for now
- Add support for multiple image sizes
- Increase the concurrency limit in vips Config
- Use the context to try cancel an image generation

- Write a non worker based request handler to compare performance
  - Its noticabily slow

- Add support to fetch image from url
- Cache the image in tmpfs
- Try reducing image quality.
  - Dynamically decide the quality based on image size
  - For larger images reduce the quality more*

- Replace the JobQueue with Queue interface
- And check redis/zeromq

pprof blocking profile shows 67.99% of total time is spent waiting (chanrecv1).

This suggests:

- Workers are blocked, waiting for jobs.
- Dispatcher is blocked, waiting for workers.
- No matter what I do, `Throuput` remains `2.0xrps`. Aim is for `8.6rps`.

- Get rid of the Workerpool Dispatcher pattern.
- Start with a single synchronous one
  - `Throughput: 2.9rps`
- With a single channel single worker:
  - `Througput: 2.1rps`
- With a single channel/queue but 4 workers:
  - `Throughput: 3.15 rps`, `Average Latency 1.3729 secs`
- With two queues, one for fetch one for process. Using 4 workers each:
  - `Throughput: 3.07rps`, `Average Latency: 1.4645 secs`, but `Request Distribution has improved`.
  - Meaning more smoother load handling at various percentiles.
  - This reduction could be due to impedance mismatch between `Fetch` and `Process`
  - Previously trace results reveal, Fetch from tmpfs around `40-100ms`, and Process at an average of `700ms` for 3.1mb image down to 120x240px webp
- With two queues for `fetch` and `process`, but 2 fetcher and 4 processors.
  - Performs worse, but still has a throughput of `3+`. So doesn't help much. Probably because system is real time and not a job processor.

- Trying dynamic scaling. With this we have increase. but not by much. 90% percentile has come down.
